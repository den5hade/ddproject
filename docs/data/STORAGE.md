# Storage (S3)

How binary artifacts are stored, named and accessed.

## Bucket layout

```text
S3
│
├── original/        source files as uploaded
├── converted/       Marker output (Markdown/JSON)
└── derived/         ai-worker artifacts
```

## Naming convention (immutable IDs)

```text
medical-records/{medical_record_id}/
    documents/{document_id}/
        versions/{version_id}/
            original.pdf
            marker.md
            marker.json
```

Example:

```text
medical-records/01JABC.../
    documents/01JDEF.../
        versions/01JXYZ.../
            original.pdf
```

Why: immutable UUIDs avoid version/rename churn and keep access control
aligned with `document_id` / `version_id`.

## Access rules

- **Never expose S3 keys directly to clients.**
- Uploads and downloads always use **presigned URLs** (short-lived, scoped).
- Binary payloads never stream through account-api; the client talks to S3
  directly (large PDFs must not pass through the API servers).

## Upload workflow

1. `POST /patients/{patient_id}/documents` → account-api creates metadata and
   returns a presigned upload URL.
2. Client uploads the file directly to S3.
3. `POST /documents/{id}/upload-confirm` → account-api verifies the object,
   creates `DocumentVersion` v1, creates a processing job, publishes
   `document.uploaded`.

## Download

Always via presigned GET URLs generated by account-api after access checks.
A presigned link without `upload-confirm` does not create a viewable document.
