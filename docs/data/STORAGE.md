# Storage (S3)

How binary artifacts are stored, named and accessed.

## Bucket layout

```text
S3
│
├── original/        source files as uploaded (normalized/validated by objectstorage-worker)
├── converted/       Marker output (Markdown/JSON)
└── derived/         ai-worker artifacts
```

## Naming convention (immutable IDs)

```text
tenants/{tenant_id}/patients/{patient_id}/documents/{document_id}/
    versions/{version_id}/
        original.pdf
        marker.md
        marker.json
```

Example:

```text
tenants/acme/patients/01JABC.../documents/01JDEF.../
    versions/01JXYZ.../
        original.pdf
```

Why: immutable UUIDs avoid version/rename churn and keep access control
aligned with `document_id` / `version_id`. The tenant prefix keeps every
tenant's objects scoped for lifecycle/billing operations.

## Access rules

- **Never expose S3 keys directly to clients.**
- Downloads always use **presigned GET URLs** (short-lived, scoped) generated
  by account-api after access checks.
- Uploads never use presigned URLs: the client posts the binary **through
  account-api**, which stages it in a shared temp directory and hands it to the
  objectstorage-worker for normalization + upload.
- Binary payloads never travel over RabbitMQ — events carry IDs + storage keys
  only.

## Upload workflow

1. `POST /patients/{patient_id}/documents` (multipart) → account-api validates
   size/mime, stages the file in `STORAGE_TEMP_DIR`, creates `Document` +
   `DocumentVersion` v1 (`status=pending`) + a `PDF_CONVERSION` job, and
   publishes `document.upload.requested` (payload carries `temp_path`, never
   the binary).
2. **objectstorage-worker** consumes the event, reads the staged file from the
   shared temp dir, re-validates mime/size, computes a SHA-256 checksum, and
   uploads it under the immutable key
   `tenants/{tenant}/patients/{patient}/documents/{document}/versions/{version}/original.{ext}`.
3. objectstorage-worker publishes `document.stored`; account-api persists the
   storage key/checksum and sets `document.status = processing`, then publishes
   `document.uploaded`.
4. The processing pipeline (marker → ai-worker) continues via
   `document.converted` / `document.analysis.completed`.

## Download

Always via presigned GET URLs generated by account-api after access checks. A
download returns `503` if object storage is not configured.

## Shared temp directory

`STORAGE_TEMP_DIR` (`uploads/` in the compose stack) is a filesystem shared
between account-api and objectstorage-worker. Files there are transient:
account-api cleans up on publish failure and the worker cleans up after a
successful upload.
