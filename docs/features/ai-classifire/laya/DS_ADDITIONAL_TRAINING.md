Отличный сценарий. Судя по вашему нормализатору, вы уже продумали пайплайн до Laya — у вас на выходе получается `NormalizedDocument` с сохранённой структурой (headings, tables, paragraphs). Это важно, потому что Laya может использовать эти структурные сигналы.

Ниже — пример того, как упаковать ваш `NormalizedDocument` в «состояние» для Laya и какие типизированные вопросы задать для дообучения.

---

### 🧩 Состояние (state)

В Laya «состояние» — это текст, письмо, тикет или JSON-документ, который модель анализирует. Поскольку ваш `NormalizedDocument` содержит структурированные поля, логичнее всего передавать их как JSON — так Laya увидит и общий текст, и структурные сигналы (заголовки, таблицы).

```python
state = {
    "doc_type_hint": "medical_report",          # необязательный контекст от сервиса
    "headings": doc.headings,
    "tables": doc.tables,
    "paragraphs": doc.paragraphs,
    "raw_text": doc.raw_text,
    "metadata": doc.metadata,                   # table_count, heading_count, paragraph_count
}
```

Можно ограничиться `raw_text`, но если таблицы в лабораторных бланках несут ключевые строки (например, «Гемоглобин | 145 | г/л»), их стоит передавать отдельно — Laya умеет работать с таблицами как с блоками.

---

### ❓ Типизированные вопросы (questions)

В вашей задаче есть несколько уровней классификации. Их можно объединить в один вызов `router.predict(state, questions)` — Laya ответит на все вопросы за один forward pass.

#### 1. Тип документа — `choice`

Основной вопрос: что это за документ.

```python
"document_type": {
    "type": "choice",
    "instructions": "Определи тип медицинского документа по его содержанию и структуре.",
    "criteria": {
        "lab_result": "лабораторное исследование: анализы крови, мочи, биохимия, таблицы с показателями и референсными интервалами",
        "discharge_summary": "выписка: эпикриз, история госпитализации, диагноз, рекомендации, даты поступления и выписки",
        "instrumental_study": "инструментальное исследование: УЗИ, МРТ, КТ, ЭКГ, ЭхоКГ, описание снимков и заключение врача-диагноста",
        "outpatient_note": "амбулаторная запись: приём врача, жалобы, назначения, осмотр",
        "referral": "направление: документ на консультацию или исследование",
        "other": "иное: не относится к перечисленным категориям",
    },
}
```

Это базовый вопрос, который вероятнее всего будет использоваться в вашем сервисе.

#### 2. Подтип — `choice` (опционально)

Если тип определён как `lab_result`, можно сразу уточнить, какая это лаборатория:

```python
"lab_subtype": {
    "type": "choice",
    "instructions": "Уточни вид лабораторного исследования.",
    "criteria": {
        "cbc": "общий анализ крови: эритроциты, гемоглобин, лейкоциты, тромбоциты",
        "biochemistry": "биохимия: глюкоза, АЛТ, АСТ, креатинин, билирубин",
        "urinalysis": "анализ мочи: цвет, плотность, белок, лейкоциты",
        "coagulogram": "коагулограмма: АЧТВ, МНО, фибриноген",
        "hormones": "гормоны: ТТГ, Т3, Т4, кортизол",
        "other_lab": "другое лабораторное исследование",
    },
}
```

#### 3. Уверенность / риск ошибки — `noul`

Полезно для gating: если модель не уверена в типе, отправить документ на ручную проверку.

```python
"needs_human_review": {
    "type": "noul",
    "instructions": "Требует ли этот документ ручной проверки из-за неоднозначности типа или структуры?",
}
```

#### 4. Срочность — `score` (опционально)

Если документ может содержать критические значения:

```python
"criticality": {
    "type": "score",
    "instructions": "Насколько критичны данные в документе?",
    "criteria": ["routine", "attention", "critical"],
}
```

### 🧪 Полный пример вызова

```python
from laya import Router

router = Router()

state = {
    "raw_text": doc.raw_text,
    "headings": doc.headings,
    "tables": doc.tables,
    "metadata": doc.metadata,
}

questions = {
    "document_type": {
        "type": "choice",
        "instructions": "Определи тип медицинского документа.",
        "criteria": {
            "lab_result": "лабораторное исследование с таблицами показателей",
            "discharge_summary": "выписка с диагнозом и рекомендациями",
            "instrumental_study": "описание УЗИ, МРТ, КТ, ЭКГ",
            "outpatient_note": "амбулаторная запись приёма",
            "other": "иное",
        },
    },
    "needs_human_review": {
        "type": "noul",
        "instructions": "Требует ли документ ручной проверки?",
    },
}

result = router.predict(state, questions, model="multilingual")  # если документы на русском

print(result["answers"]["needs_human_review"]["noul"])
```

### 📚 Как это превратить в датасет для дообучения

Для ноутбука `laya_finetune_typed_decisions_2xT4_kaggle.ipynb` вам нужно собрать набор примеров, где для каждого документа известен правильный ответ. Формат — список словарей:

```python
[
    {
        "state": {"raw_text": "...", "headings": [...], "tables": [...]},
        "questions": { ... },           # та же схема, что выше
        "answers": {
            "document_type": {"choice": "lab_result"},
            "needs_human_review": {"noul": 0.0},
        },
    },
    ...
]
```

Ключевые моменты при подготовке данных:

- **Разметка должна быть согласованной.** Если один и тот же тип документа размечен по-разному, модель не обучится.
- **Дисбаланс классов.** Если лабораторных исследований 90%, а выписок 5%, модель может просто выучить majority class. Добавьте примеров редких классов или используйте взвешивание.
- **Калибровка.** После обучения обязательно прогоните ноутбук до шага temperature fitting на отложенной выборке — базовые вероятности Laya переуверенные.
- **Noul-вопрос.** Для него в `answers` указывайте 0.0 или 1.0 (P(true)), а не строку.

## 🔍 Что здесь важно

**1. State — это ваш `NormalizedDocument` в виде dict.**
Поля `headings`, `tables`, `paragraphs`, `metadata` — ровно то, что отдаёт `MarkdownNormalizer.normalize()`. Laya принимает JSON-состояние, так что конвертация тривиальна: `dataclasses.asdict(doc)`.

**2. `raw_text` — уже канонизирован (casefold).**
В вашем нормализаторе `_canonical()` делает casefold, поэтому в примере всё в нижнем регистре. Это нормально — Laya всё равно прогонит токенизацию, а для matching регистр не важен.

**3. `questions` — общая схема для всего датасета.**
Все записи должны использовать **одну и ту же схему вопросов**, иначе ноутбук не соберёт тензоры. Если хотите обучать на подмножестве вопросов — лучше сделать отдельный датасет.

**4. `answers` — эталон.**
- Для `choice` — строка, точно совпадающая с одним из ключей `criteria`.
- Для `noul` — число от 0.0 до 1.0 (P(true)).
- Для `score` — целое или float в пределах шкалы.

**5. Добавил два новых вопроса, которых не было в прошлом ответе:**
- `contains_personal_data` — полезно для вашего сервиса, чтобы автоматически решать, можно ли логировать документ или отправлять его во внешние системы.
- `appointment_ticket` — отдельная категория для талонов на приём, потому что в вашем примере это именно талон, а не выписка и не лабораторное исследование.

Ноутбук `laya_finetune_typed_decisions_2xT4_kaggle.ipynb` читает именно такой формат. Дальше — стандартный цикл: обучение, калибровка температур, оценка на отложенной выборке.

Если хотите, могу собрать **вторую запись** — например, для лабораторного исследования с таблицей показателей, чтобы у вас было по одному примеру на каждый из трёх типов документов.

«Разметка должна быть согласованной» — это значит, что **одинаковые по смыслу документы должны иметь одинаковый эталонный ответ** во всём датасете. Если два похожих документа размечены по-разному, модель не сможет выучить закономерность и будет путаться.

Проще говоря: правила разметки должны быть **едиными и явными**, а не зависеть от настроения или памяти того, кто размечал.

## 🔴 Пример несогласованной разметки

Допустим, у вас есть три талона на приём к врачу, очень похожих по структуре:

**Запись 1**
```python
"document_type": {"choice": "appointment_ticket"}
```

**Запись 2**
```python
"document_type": {"choice": "other"}          # ← разметчик решил, что это «иное»
```

**Запись 3**
```python
"document_type": {"choice": "outpatient_note"} # ← а тут вообще другой класс
```

Все три — талоны на приём. Но эталоны разные. Модель видит одинаковые входы и разные ответы — она не может понять, что от неё хотят. В лучшем случае выучит majority-класс, в худшем — будет выдавать случайный из трёх.

---

## 🟢 Пример согласованной разметки

Вы заранее договорились: **«талон на приём — это документ, где есть номер талона, дата/время приёма, адрес и кабинет, но нет клинического содержания (жалоб, диагноза, назначений)»**.

Тогда все три записи получают один и тот же эталон:

```python
"document_type": {"choice": "appointment_ticket"}
```

Теперь модель видит одинаковые входы и одинаковые ответы — она учится именно тому, что вы хотите.

---

## 📋 Где чаще всего возникает несогласованность

1. **Границы между похожими классами.**
   - Талон на приём vs амбулаторная запись (если в талоне вдруг есть жалобы).
   - Лабораторное исследование vs инструментальное (если в лабораторном бланке есть УЗИ-описание).
   - Выписка vs направление (если выписка содержит направление на дообследование).

   Нужно **явно прописать в инструкции вопроса**, что куда относится, и следовать этому.

2. **Разные разметчики.**
   Если датасет размечали несколько человек, у каждого свои представления о границах классов. Нужен **гайд по разметке** (annotation guide) и, желательно, перекрёстная проверка.

3. **Изменение правил по ходу разметки.**
   Разметили 500 документов, потом решили, что талон — это отдельный класс, и переразметили только следующие 200. Первые 500 остались со старой разметкой. Это тоже несогласованность.

4. **Неоднозначные документы.**
   Документ, который одинаково похож на два класса. Если такие есть — либо вводите правило («при сомнении выбирай X»), либо отдельный класс `ambiguous`, либо исключаете из датасета.

---

## 🛠 Как проверить согласованность

**1. Единый гайд по разметке.**
Заведите документ, где для каждого класса написано:
- что в него входит;
- что не входит;
- примеры;
- как разрешать спорные случаи.

**2. Проверка на дублях.**
Если у вас есть почти одинаковые документы (например, один и тот же талон из разных источников), они должны иметь одинаковый эталон. Прогоните датасет через дедупликацию и сравните метки.

**3. Перекрёстная разметка.**
Дайте 50–100 документов двум разметчикам независимо. Посчитайте согласие (Cohen's kappa). Если ниже 0.8 — правила размытые, нужно уточнять.

**4. Метрика на отложенной выборке по классам.**
После дообучения посмотрите confusion matrix. Если модель путает именно те классы, где у вас были сомнения при разметке, — скорее всего, проблема в несогласованности, а не в модели.

**5. Единый источник истины.**
Если документы приходят из разных систем (лаборатория, поликлиника, стационар), убедитесь, что для каждой системы правила разметки одинаковые. Иначе модель выучит «разметку по источнику», а не по содержанию.

---

## 💡 Коротко

Согласованная разметка — это когда **для любого документа в датасете эталонный ответ определяется одними и теми же правилами**, независимо от того, кто и когда размечал. Если правила разные — модель не обучится, сколько бы данных вы ни собрали.
