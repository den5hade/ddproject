# Медицинская платформа персональной медицинской истории

## 1. Назначение документа

Этот документ описывает общую концепцию продукта, его участников, основные домены, пользовательские сценарии и процессы.

Документ намеренно **не определяет техническую архитектуру и конкретные технологии реализации**. Его задача — зафиксировать, **что представляет собой продукт, для кого он существует, какие проблемы решает и какие процессы должен поддерживать**.

В дальнейшем этот документ может использоваться как основа для:

- проектирования базы данных;
- определения API;
- проектирования пользовательского интерфейса;
- выбора технической архитектуры;
- разработки AI-процессов;
- интеграции с медицинскими организациями;
- формирования roadmap продукта.

---

# 2. Идея продукта

Платформа предоставляет человеку единое цифровое пространство для хранения и использования собственной медицинской истории.

Пользователь может получать медицинские документы из разных источников:

- самостоятельно загружать документы;
- получать документы от медицинских организаций;
- получать документы от специалистов;
- добавлять результаты обследований;
- хранить выписки;
- хранить диагнозы;
- хранить результаты лабораторных исследований;
- хранить результаты инструментальных исследований;
- хранить изображения и другие медицинские материалы.

Вместо того чтобы медицинская информация была распределена между:

- разными клиниками;
- лабораториями;
- электронной почтой;
- бумажными документами;
- мессенджерами;
- файлами на телефоне;
- разными медицинскими информационными системами,

пользователь получает **единое место для своей медицинской истории**.

---

# 3. Основная ценность продукта

## Для пользователя

Пользователь получает:

> **Единую персональную медицинскую историю, собранную из разных источников.**

Он может:

- получать документы;
- хранить документы;
- просматривать документы;
- видеть историю обследований;
- видеть историю посещений специалистов;
- предоставлять доступ специалистам;
- предоставлять доступ медицинским организациям;
- получать новые документы непосредственно от медицинских организаций;
- постепенно получать аналитическую информацию на основании накопленной истории.

---

# 4. Основная проблема пользователя

Сегодня медицинская информация человека часто фрагментирована.

Например:

```text
Лаборатория
   │
   └── email с PDF

Клиника №1
   │
   └── личный кабинет клиники

Клиника №2
   │
   └── бумажная выписка

Частный врач
   │
   └── документ в мессенджере

Рентген-центр
   │
   └── ссылка на исследование
```

В результате у человека нет единой картины собственной медицинской истории.

Платформа должна постепенно превращать эти разрозненные документы в:

```text
                    ПОЛЬЗОВАТЕЛЬ
                         │
                 Медицинская история
                         │
        ┌────────────────┼────────────────┐
        │                │                │
     Анализы          Визиты          Исследования
        │                │                │
     Диагнозы         Выписки        Изображения
        │                │                │
        └────────────────┼────────────────┘
                         │
                    Аналитика
                         │
                  AI-помощник
```

# 5. Основные участники системы

Продукт предполагает несколько основных типов участников.

## 5.1. Client

Человек, которому принадлежит медицинская история.

Основной пользователь платформы.

Он может:

- создать аккаунт;
- войти в систему;
- загружать документы;
- просматривать документы;
- получать документы от организаций;
- предоставлять доступ специалистам;
- предоставлять доступ организациям;
- управлять доступом;
- просматривать медицинскую историю;
- получать аналитическую информацию;
- в будущем использовать AI-функции.

---

## 5.2. Specialist

Медицинский специалист.

Например:

- врач;
- диагност;
- консультант;
- специалист лаборатории;
- другой авторизованный медицинский работник.

Специалист может получить доступ к медицинской истории пользователя, если пользователь предоставил такой доступ.

Специалист может:

- просматривать разрешённые документы;
- просматривать медицинскую историю;
- добавлять документы;
- добавлять результаты посещения;
- добавлять заключения;
- формировать новые медицинские записи;
- в будущем использовать AI-инструменты для работы с историей пациента.

---

# 6. Organisation

`Organisation` является отдельным крупным доменом продукта.

Организация представляет юридическое или операционное объединение специалистов, работающих с пациентами.

Примеры:

- клиника;
- лаборатория;
- диагностический центр;
- больница;
- медицинский центр;
- страховая организация;
- другая организация, работающая с медицинскими данными.

Организация может использовать платформу одновременно в двух ролях.

### Роль 1 — источник документов

Организация отправляет пользователю документы.

Например:

```text
Клиника
   ↓
результат анализа
   ↓
платформа
   ↓
пользователь получает уведомление
   ↓
пользователь открывает документ
```

### Роль 2 — рабочее пространство

Организация может использовать платформу как дополнительное пространство для работы с пациентами.

Например:

```text
Organisation
    │
    ├── Specialists
    │
    ├── Clients
    │
    └── Documents
```

Это позволяет постепенно превратить платформу из персонального хранилища документов в **связующее звено между пациентом и медицинскими организациями**.

---

# 7. Specialist внутри Organisation

Специалист может принадлежать организации.

Например:

```text
Organisation:
    Клиника "А"

        ├── Doctor
        │     Иванов И.И.
        │
        ├── Doctor
        │     Петрова А.А.
        │
        └── Administrator
              ...
```

При этом специалист может иметь собственные права внутри организации.

Например:

- просмотр пациентов;
- добавление документов;
- просмотр документов;
- работа с пациентами;
- просмотр медицинской истории;
- использование AI-инструментов.

---

# 8. Administrator

Администратор платформы отвечает за функционирование самой системы.

Он не должен автоматически получать доступ к медицинской истории пользователей только потому, что имеет административную роль.

Административные права и права доступа к медицинским данным должны быть концептуально разделены.

Администратор может управлять:

- пользователями;
- организациями;
- специалистами;
- системными настройками;
- безопасностью;
- статусами процессов;
- поддержкой;
- аудитом.

---

# 9. Модель отношений между участниками

Основная модель:

```text
                         PLATFORM
                            │
              ┌─────────────┴─────────────┐
              │                           │
           CLIENT                    ORGANISATION
              │                           │
              │                    ┌──────┴──────┐
              │                    │             │
              │               SPECIALISTS    STAFF
              │
              │
              └──────────────┐
                             │
                        ACCESS GRANT
                             │
                             ▼
                        SPECIALIST
                        ORGANISATION
```

Пользователь является владельцем своей медицинской истории.

Организация или специалист получает доступ к ней только в рамках предоставленных полномочий.

---

# 10. Регистрация и вход пользователя

Пользователь может зарегистрироваться через:

- email;
- номер телефона.

Основной принцип авторизации:

> пользователь подтверждает владение email или номером телефона с помощью одноразового пароля.

Процесс:

```text
Пользователь
    ↓
вводит email / телефон
    ↓
получает одноразовый пароль
    ↓
вводит пароль
    ↓
система подтверждает личность
    ↓
пользователь получает доступ к аккаунту
```

Отдельный постоянный пароль пользователя на данном этапе не является обязательной частью пользовательского сценария.

---

# 11. Персональная медицинская история

Главный объект продукта — **медицинская история пользователя**.

Она состоит из документов и связанных с ними медицинских событий.

Например:

```text
Медицинская история
│
├── 2026-01-15
│   └── Анализ крови
│
├── 2026-02-10
│   └── Приём кардиолога
│
├── 2026-03-01
│   └── ЭКГ
│
├── 2026-03-15
│   └── Выписка
│
└── 2026-04-20
    └── Анализ крови
```

В будущем история должна позволять пользователю видеть не только список файлов, но и **хронологию медицинских событий**.

---

# 12. Документ

Документ является одним из центральных объектов системы.

Документ может быть:

- PDF;
- JPEG;
- PNG;
- другим поддерживаемым форматом.

Документ может представлять:

- лабораторное исследование;
- выписку;
- диагноз;
- заключение специалиста;
- результат инструментального исследования;
- результат визуальной диагностики;
- назначение;
- рецепт;
- справку;
- медицинское заключение;
- другой медицинский документ.

---

# 13. Источник документа

Каждый документ должен иметь источник.

Основные варианты:

```text
USER
SPECIALIST
ORGANISATION
SYSTEM
```

### USER

Пользователь самостоятельно загрузил документ.

### SPECIALIST

Документ добавил медицинский специалист.

### ORGANISATION

Документ поступил от медицинской организации.

### SYSTEM

Документ был создан самой системой на основании другого процесса.

---

# 14. Самостоятельная загрузка документа

Основной пользовательский сценарий:

```text
Пользователь
    ↓
выбирает PDF / JPEG
    ↓
загружает документ
    ↓
система принимает документ
    ↓
документ появляется в истории
    ↓
документ обрабатывается
    ↓
из документа извлекается структурированная информация
    ↓
пользователь получает результат
```

Пользователь не обязан понимать, как именно документ был обработан.

Для него процесс должен выглядеть максимально просто.

---

# 15. Обработка документа

С точки зрения продукта процесс выглядит следующим образом:

```text
Original document
        ↓
Document processing
        ↓
Unstructured representation
        ↓
AI extraction
        ↓
Canonical structured representation
        ↓
Structured medical document
        ↓
Medical history
        ↓
Analytics
```

Пользователь видит результат обработки, но внутренние этапы являются частью системы обработки документов.

---

# 16. Canonical representation

Внутренним структурированным представлением документа является `canonical.json`.

Он представляет собой нормализованное описание содержимого медицинского документа.

Например, для лабораторного исследования:

```text
Document
│
├── document type
├── date
├── laboratory
├── test
│
└── results
      ├── indicator
      ├── value
      ├── unit
      ├── reference range
      └── interpretation
```

Canonical representation является основой для дальнейшего использования данных.

Она может использоваться для:

- отображения информации;
- формирования структурированного документа;
- аналитики;
- поиска;
- построения медицинской истории;
- AI-анализа;
- помощи специалистам.

---

# 17. Structured Markdown

На основании структурированного представления формируется структурированный Markdown-документ.

Он предназначен для:

- удобного чтения;
- последующей обработки;
- хранения структурированной информации в человекочитаемом формате;
- использования в будущих AI-процессах.

Markdown содержит структурированную медицинскую информацию и metadata документа.

---

# 18. Медицинская аналитика

На первом этапе аналитика является простой.

Она может строиться на основании накопленных структурированных данных.

Например:

```text
Гемоглобин

2026-01-10   132
2026-03-15   137
2026-06-20   135
```

Пользователь может видеть:

- изменения показателей;
- историю исследований;
- даты исследований;
- повторяющиеся исследования;
- доступные значения;
- простые тенденции.

Важно:

> на первом этапе система не должна заменять врача и самостоятельно устанавливать медицинские диагнозы.

Её задача — организовать и показать информацию, которая уже присутствует в медицинских документах.

---

# 19. Доступ к медицинской истории

Пользователь является владельцем своей медицинской информации.

Он может предоставить доступ:

- отдельному специалисту;
- организации.

Например:

```text
Client
   │
   ├── Dr. Ivanov
   │      └── access
   │
   └── Clinic ABC
          └── access
```

---

# 20. Управление доступом

Пользователь должен иметь возможность:

- предоставить доступ;
- определить область доступа;
- увидеть, кому предоставлен доступ;
- изменить доступ;
- отменить доступ.

В будущем доступ может быть более детальным.

Например:

```text
Full medical history
Laboratory results
Imaging
Prescriptions
Doctor visits
Discharge summaries
```

На первом этапе достаточно поддержать понятную модель:

```text
view
add
```

---

# 21. Просмотр истории специалистом

Если пользователь предоставил специалисту доступ, специалист получает возможность:

```text
Patient
   ↓
Medical history
   ↓
Documents
   ↓
Structured information
```

Специалист может просматривать документы, относящиеся к разрешённой медицинской истории.

---

# 22. Добавление документа специалистом

После приёма специалист может добавить новый документ.

Например:

```text
Пациент пришёл на приём
        ↓
Специалист проводит консультацию
        ↓
Формирует заключение
        ↓
Добавляет документ
        ↓
Документ появляется
в медицинской истории пациента
```

Пользователь получает новый документ в своей истории.

---

# 23. Медицинская организация как источник документов

Отдельный важный сценарий:

> организация самостоятельно отправляет медицинский документ пользователю.

Например:

```text
Пациент сдал анализы в лаборатории
              ↓
          Лаборатория
              ↓
       передаёт документ
              ↓
          Платформа
              ↓
       определяет пользователя
              ↓
       сохраняет документ
              ↓
       запускает обработку
              ↓
       отправляет уведомление
              ↓
           Пациент
```

Пользователю не нужно самостоятельно загружать документ.

---

# 24. Создание пользователя организацией

Если организация отправляет документ человеку, у которого ещё нет аккаунта, платформа может создать пользователя на основании его email.

Например:

```text
Organisation
      ↓
email: user@example.com
      ↓
пользователь отсутствует
      ↓
создаётся Client
      ↓
документ сохраняется
      ↓
пользователю отправляется уведомление
```

Пользователь после этого может открыть сервис и войти с помощью одноразового пароля.

---

# 25. Уведомления

Одной из важных функций платформы является доставка медицинских документов пользователю.

Например:

```text
Медицинская организация
        ↓
Новый результат
        ↓
Платформа
        ↓
Notification
        ↓
Email / SMS / другие каналы
        ↓
Пользователь
```

Сообщение должно сообщать пользователю о наличии нового документа, не раскрывая лишние медицинские данные непосредственно в уведомлении.

Например:

> Вам доступен новый медицинский документ.

Пользователь переходит в сервис и после авторизации получает доступ к документу.

---

# 26. Ценность для медицинской организации

Для медицинской организации платформа предоставляет дополнительный слой между её внутренними системами и пациентом.

Модель:

```text
Medical organisation
        │
        │
        ▼
    PLATFORM
        │
        ├── Document delivery
        ├── Notifications
        ├── User access
        ├── Document storage
        └── AI processing
        │
        ▼
      Patient
```

Организации не обязательно самостоятельно строить весь пользовательский experience вокруг доставки медицинских документов.

Платформа становится промежуточным пользовательским слоем.

---

# 27. Ценность для медицинской организации

Основные преимущества:

### 27.1. Доставка документов

Организация может передавать:

- результаты анализов;
- выписки;
- заключения;
- диагнозы;
- результаты исследований;
- изображения;
- другие документы.

### 27.2. Уведомления

Платформа может уведомлять пользователя о готовности результата.

### 27.3. Пользовательский кабинет

Организации не обязательно создавать собственный сложный пользовательский кабинет для каждого сценария работы с документами.

### 27.4. Хранение документов

Документы могут становиться частью долгосрочной медицинской истории пользователя.

### 27.5. Единая история пациента

Пользователь может получать документы не только от одной организации.

Это создаёт ценность, которую отдельная клиника не может полностью обеспечить:

> история пациента становится независимой от конкретной медицинской организации.

# 32. Будущий AI-анализ

После накопления достаточного количества структурированных данных появляется следующий уровень продукта.

Система получает возможность анализировать не отдельный документ, а **медицинскую историю пользователя целиком**.

Например:

```text
Documents
    ↓
Canonical data
    ↓
Medical history
    ↓
Longitudinal analysis
    ↓
AI
```

AI сможет помогать:

- находить изменения показателей;
- находить повторяющиеся исследования;
- связывать события во времени;
- формировать краткое резюме истории;
- находить потенциально важные изменения;
- готовить информацию к посещению специалиста;
- отвечать на вопросы пользователя по его документам;
- помогать специалисту быстрее ознакомиться с историей пациента.

# 38. Ключевой принцип владения данными

Центральный принцип продукта:

> **Медицинская история принадлежит пользователю, а не организации.**

Организация является источником документов и может иметь разрешённый доступ.

Специалист может иметь разрешённый доступ.

Но медицинская история объединяет информацию из разных источников вокруг одного пользователя.

---

# 39. Ключевой принцип переносимости

Пользователь не должен становиться зависимым от одной медицинской организации.

Например:

```text

Clinic A
     ↓
documents

2027
Clinic B
     ↓
documents

2028
Hospital C
     ↓
documents
```

Вся информация продолжает находиться в одной медицинской истории пользователя.

---

# 40. Ключевой принцип независимости источника

Платформа должна рассматривать медицинский документ прежде всего как **информацию пациента**, а не как собственность конкретного источника.

Источник сохраняется:

```text

    organisation
    specialist
    user
```

но документ становится частью единой истории пользователя.

# 44. Что является продуктом, а что является внутренним процессом

Важно разделять эти понятия.

Для пользователя продукт:

```text
Моя медицинская история
```

Для специалиста:

```text
История пациента
```

Для организации:

```text
Доставка документов + взаимодействие с пациентом
```

Для внутренней системы:

```text
Document
 → processing
 → canonical data
 → structured document
 → medical history
 → analytics
 → AI
```

То есть Marker, AI extraction, canonical JSON и Markdown — это **механизмы реализации продукта**, а не сами продуктовые сущности.

  ▼

  │
  │ contains
  ▼

Это является фундаментом всего продукта.

а на вопрос:

> **«Какие конкретно сущности существуют в каждом домене и как они связаны между собой?»**

То есть следующим шагом логично описать:

и для каждой сущности определить:

- назначение;
- кто её создаёт;
- кто может её видеть;
- кто может её изменять;
- жизненный цикл;
- связи с другими сущностями;
- обязательные и необязательные атрибуты.

Только **после этого** имеет смысл переходить к технической модели БД, API, очередям и архитектуре сервисов.
